# Stack Comparison

This comparison is intentionally practical. The point is not that one stack is
always best. The point is that identity integration work often crosses stack
layers, and the engineer needs enough fluency to evaluate each path.

| Track | Why it matters | Portfolio signal |
| --- | --- | --- |
| Angular / TypeScript | Makes authentication and callback flows visible from the browser side. | Frontend expertise connected to integration reality. |
| NestJS / Node.js | Fast API prototyping, DTOs, Swagger, SAML endpoint experiments. | Backend API literacy in a TypeScript ecosystem. |
| ASP.NET Core / .NET 8 | Strong typed backend model, controllers, OpenAPI and certificate-aware helpers. | C# service awareness beyond frontend work. |
| Java / Spring | Enterprise integration surface for SOAP/WSDL, CXF, XML security and OpenSAML-oriented flows. | Ability to work with older but important backend integration stacks. |
| SAML / certificates / XML | Core identity and protocol validation complexity. | Security-aware debugging and protocol literacy. |
| Swagger / OpenAPI / generated models | Keeps contracts inspectable and consumable by frontend code. | Contract-first thinking and maintainable integration work. |

## How The Tracks Complement Each Other

Angular makes browser-visible behavior testable, NestJS keeps a
TypeScript-oriented API path close to the frontend, .NET provides a strongly
typed backend and OpenAPI workflow, and Java remains important for SOAP/WSDL,
CXF and XML security ecosystems. The case study is about evaluating those
layers together instead of treating the frontend as isolated from the
integration stack.

## Tradeoff Themes

- NestJS is convenient when the team wants TypeScript on both sides of the API.
- .NET gives a strong typed backend and straightforward OpenAPI workflows.
- Java remains important for enterprise SOAP/WSDL and XML security ecosystems.
- Angular benefits from generated models and visible API contracts regardless of
  which backend stack wins.
